Most monitoring setups fail the first time a real incident hits.

The failure is rarely a lack of data. Usually, the opposite happens: teams build dashboards full of decorative banners, unformatted byte counters, and generic uptime checks that stay green even while background workers die silently. When an on-call engineer gets paged at 3:00 AM, they do not need conversational paragraphs or un-actionable charts. They need immediate visibility into queue lag, error rates, and concrete diagnostic commands.

When instrumenting the production infrastructure for my messaging and distributed worker platform (`ezmsg`), I designed our observability stack on **Splunk Observability Cloud** around three requirements:

1. **High-density telemetry**: Every card must show a trend, not just a static number.
2. **Accurate worker health**: Detect deadlocks and thread stalls, not just HTTP 200 responses.
3. **Centralized alert runbooks**: Decouple detection logic from notification formatting so alerts always contain exact triage commands.

## The Telemetry Pipeline

Our production stack runs FastAPI backend services, a fleet of background stream workers, Redis Streams for message brokering, and PostgreSQL. 

Instead of sending metrics directly from application code to cloud endpoints, all telemetry passes through a local containerized **Splunk OpenTelemetry Collector**.

### Collector Configuration Choices

The OpenTelemetry Collector handles Prometheus metric scraping, memory protection, and export over TLS. In high-throughput streaming environments, three configuration choices matter:

1. **Memory Ballast (`memory_ballast`)**: Allocating 20% of container memory as ballast stabilizes garbage collection cycles during traffic bursts, preventing the collector from dropping samples.
2. **Memory Limiter (`memory_limiter`)**: Sets a hard ceiling at 80% utilization with a 20% spike limit. If memory nears the ceiling, the collector sheds non-critical telemetry rather than crashing.
3. **Batching (`batch`)**: Flushes every 5 seconds or whenever 8,192 metrics accumulate, reducing HTTP/gRPC overhead to the Splunk ingest endpoint.

```yaml
# OpenTelemetry Collector Core Pipeline
receivers:
  prometheus:
    config:
      scrape_configs:
        - job_name: 'ezmsg-services'
          scrape_interval: 10s
          static_configs:
            - targets: ['ezmsg-user-api:8000', 'ezmsg-admin-api:8000']
        - job_name: 'ezmsg-workers'
          scrape_interval: 10s
          static_configs:
            - targets:
                - 'ezmsg-worker-prod:8000'
                - 'ezmsg-worker-sim:8000'
                - 'ezmsg-worker-ai-index:8000'
                - 'ezmsg-worker-bundle:8000'

processors:
  memory_ballast:
    size_in_percentage: 20
  memory_limiter:
    check_interval: 2s
    limit_percentage: 80
    spike_limit_percentage: 20
  batch:
    send_batch_size: 8192
    timeout: 5s

exporters:
  signalfx:
    access_token: "${SPLUNK_ACCESS_TOKEN}"
    realm: "${SPLUNK_REALM}"

service:
  pipelines:
    metrics:
      receivers: [prometheus]
      processors: [memory_ballast, memory_limiter, batch]
      exporters: [signalfx]
```

## SignalFlow: Engineering True Signals

Splunk Observability Cloud executes queries using **SignalFlow**, a streaming computation engine that evaluates timeseries at sub-second frequency. 

Writing effective SignalFlow queries requires avoiding three common mistakes:

### 1. The Worker Uptime Trap

A standard Prometheus metric for service health is `up{job="ezmsg-workers"}`. 

The problem: a Python worker process can deadlock internally or fall into an unhandled loop while its HTTP server continues responding `200 OK` on `/metrics`. A dashboard showing `up == 1` hides the fact that the queue consumer stopped processing messages.

To fix this, each worker emits an explicit heartbeat gauge, `ezm_worker_up{worker="..."}`, only when its inner task loop completes a processing cycle. 

The SignalFlow query calculates the live sum across all worker instances:

```python
A = data('ezm_worker_up').sum().publish(label='Active Workers')
```

If any worker hangs or exits, the sum immediately drops below 8, triggering an alert within 15 seconds.

### 2. Binary Unit Precision

Raw counters are difficult to interpret during incidents. If a card displays `1,700,456` bytes, an engineer must do mental math to determine whether Redis is using 1.7 MB, 17 MB, or 170 MB.

We configure the chart presentation layer to enforce binary byte scaling:
* **Value Unit**: `Byte`
* **Unit Prefix**: `Binary`
* **Maximum Precision**: `2`

Splunk automatically computes binary divisions ($1024^2$), rendering the metric clearly as **`1.62 MiB`**.

### 3. Stream Lag and Dead Letter Queues

In a streaming pipeline, consumer health is measured by **lag**, not just throughput. If ingestion outpaces processing, messages back up silently until storage saturates.

```python
# Peak consumer group lag across all stream partitions
A = data('ezm_redis_stream_consumer_lag').max().publish(label='Max Consumer Lag')

# 5-minute rolling rate of dead-letter queue insertions
B = data('ezm_dlq_messages_total').sum(over='5m').publish(label='DLQ Inflow')
```

Tracking the maximum lag across all consumer groups surfaces partition imbalances before they lead to downstream message timeouts.

## Dashboard Architecture: 12-Column SRE Layout

A good SRE dashboard is an instrument panel, not a canvas. We rebuilt our production dashboard (`HWBuSQpA0AA`) around strict density guidelines:

1. **12-Column Symmetrical Grid**: Panels follow consistent widths (`4x3` cards, `2x6` charts, `3x4` splits) so the eye can scan vertically without jagged alignments.
2. **Every Metric Card Has a Sparkline**: Single-value numbers alone do not indicate direction. A card showing `1.62 MiB` could be steady, dropping, or leaking. A 1-hour rolling sparkline embedded inside each card gives immediate historical context.
3. **Three-Tier Visual Hierarchy**:
   - **Row 1: Golden Signals** (Inbound Request Rate, HTTP 5xx Error Rate, p95 Latency, Active Worker Count).
   - **Row 2: Pipeline & Storage** (Redis Stream Throughput, Consumer Lag, DLQ Activity, Postgres Connections).
   - **Row 3: Host Infrastructure** (Available RAM in GB, CPU Idle %, Disk I/O Wait, Redis Memory RSS).
4. **SLO-Aligned Color Scales**:
   - **Green**: Nominal operation ($< 1\%$ 5xx errors, $< 75\%$ RAM).
   - **Yellow**: Warning threshold ($1\% - 5\%$ 5xx errors, $75\% - 85\%$ RAM).
   - **Red**: Breach threshold ($> 5\%$ 5xx errors, $> 85\%$ RAM, worker count $< 8$).

## Alert Architecture: Decoupling Rules from Notifications

The most common anti-pattern in alert engineering is hardcoding notification messages, recipient lists, and runbooks directly inside individual detector rules. 

When on-call rotations change or a diagnostic command is updated, engineers must edit dozens of detectors manually. Over time, runbooks drift out of date, and alert emails become noisy, context-free notifications.

### Designing the Centralized Template

We separated detector rule logic from notification delivery by creating a single, centralized SRE email template (`HWOnxSBA4AA`).

The template uses Handlebars expressions to inject runtime context dynamically:

```text
Subject:
{{#if anomalous}}[{{ruleSeverity}}] {{detectorName}}{{else}}[RESOLVED] {{detectorName}}{{/if}}

Body Structure:
- Detector Name and Severity
- Firing Status (FIRING vs. RESOLVED)
- Exact Trigger Metric Value and Breached Threshold
- Timestamp and Affected Host Dimension
- Direct Link to the Production Dashboard

Diagnostic Runbook:
1. Check active containers: docker ps
2. Inspect worker logs: docker logs --tail 100 ezmsg-worker-prod
3. Check host memory: free -h
```

### Template Constraints

When building templates for Splunk Observability Cloud, two structural constraints must be accounted for:

* **Handlebars Syntax Clashes**: Splunk parses template strings with Handlebars. If a shell command in your runbook contains double brackets (such as `docker stats --format "{{.Name}}"`), the parser interprets them as unclosed template tags and rejects the payload. Diagnostic commands must avoid double braces.
* **Detector Linkage**: Detectors link to templates by referencing the template identifier (`templateId`) in their notification rules. Separating this configuration ensures changes to on-call runbooks take effect across all linked detectors instantly.

## The Production Detector Fleet

We configured six core detectors protecting our streaming infrastructure, each linked to the centralized notification template:

| Detector Name | SignalFlow Trigger Condition | Severity | Action Triggered |
| :--- | :--- | :--- | :--- |
| **Redis Memory Spike & Leak Guard** | `data('redis_memory_used_bytes') > 500 MB` | `Critical` | Triage Redis key eviction and client buffers |
| **Redis Stream Consumer Lag** | `data('ezm_redis_stream_consumer_lag').max() > 100` for 2m | `Major` | Scale worker consumers or investigate consumer deadlocks |
| **Dead Letter Queue Activity** | `data('ezm_dlq_messages_total').sum(over='1m') > 0` | `Critical` | Inspect malformed payload schema in DLQ storage |
| **Host High RAM Utilization** | `(data('memory.used') / data('memory.total')) * 100 > 85%` for 5m | `Major` | Check container memory growth and system swap |
| **Worker Service Down** | `data('ezm_worker_up').sum() < 8` for 1m | `Critical` | Restart failed worker container |
| **API High 5xx Error Rate** | `(5xx_requests / total_requests) * 100 > 5%` for 3m | `Critical` | Inspect API trace spans and database connection pools |

## Engineering Takeaways

1. **Emit Heartbeats, Not Just Pings**: Uptime endpoints prove a web server is answering requests; they do not prove background consumers are pulling work. Measure the execution loop directly.
2. **Standardize Units**: Unscaled integers create cognitive load during triage. Enforce binary units on bytes and scale rates per minute or second.
3. **Decouple Alerts from Runbooks**: Managing notification formatting centrally eliminates configuration drift and ensures every alert delivers actionable shell commands to the engineer on call.
4. **Prioritize Density Over Decoration**: A dashboard should tell a coherent story across symmetrical rows: Golden Signals on top, internal pipeline state in the middle, and infrastructure foundations below.
